# 📜 事件溯源（Event Sourcing）

> 记录时间：2026-07-25
> 这是本项目最重要、也最需要理解的架构概念

---

## 从一个真实问题说起

你在**手机上离线**背了 20 个词，同时在**电脑上**也背了一些。
两边都改了同一个单词 `accommodate` 的进度：

```
手机：答对了 → 盒子号 3
电脑：答错了 → 盒子号 1
```

联网同步时，**听谁的？**

---

## 传统做法：只存状态

大多数应用是这么存的：

```
progress 表
┌─────────┬──────────────┬─────┐
│ user_id │ word         │ box │
├─────────┼──────────────┼─────┤
│ alice   │ accommodate  │  3  │   ← 只有"现在是几号盒子"
└─────────┴──────────────┴─────┘
```

同步时只能"**后写的覆盖先写的**"（Last Write Wins）。

**问题**：手机的数据晚 5 秒上传，就把电脑的答题记录抹掉了。用户明明答过题，进度却丢了。而且你**无从查证**到底发生了什么 —— 因为你只存了结果，没存过程。

---

## 事件溯源：存"发生了什么"，而不是"现在怎样"

换个思路：**不存当前状态，只存每一次发生的事情。**

```
answer_events 表（只追加，永不修改）
┌───────┬─────────────┬──────┬─────────┬──────────────────┬────────┐
│ user  │ word        │ mode │ correct │ answered_at      │ device │
├───────┼─────────────┼──────┼─────────┼──────────────────┼────────┤
│ alice │ accommodate │ dict │  true   │ 07-25 10:00:00   │ phone  │
│ alice │ accommodate │ dict │  true   │ 07-25 14:00:00   │ phone  │
│ alice │ accommodate │ dict │  false  │ 07-25 15:30:00   │ laptop │
└───────┴─────────────┴──────┴─────────┴──────────────────┴────────┘
```

现在"盒子号是几"不再是存起来的数字，而是**按时间顺序回放算出来的**：

```
起点：box = 1
  ↓ 10:00 答对 → box = 2
  ↓ 14:00 答对 → box = 3
  ↓ 15:30 答错 → box = 1
最终：box = 1  ✅ 确定的答案
```

**关键**：不管这三条记录以什么顺序上传，只要**按 `answered_at` 排序回放**，结果永远一样。冲突消失了。

---

## 核心概念

### 1. 事件是不可变的（Immutable）

事件表**只追加，永不 UPDATE、永不 DELETE**。

```
✅ INSERT INTO answer_events ...
❌ UPDATE answer_events SET ...
❌ DELETE FROM answer_events ...
```

理由：事件描述的是"过去发生的事实"。过去不能改。

### 2. 状态是推导出来的（Derived）

```
事件（事实）  ──回放──>  状态（推论）
```

状态是可以随时丢弃重建的。这带来一个很强的性质：**数据坏了可以修**。

### 3. 时间戳必须是"事件发生时刻"

```python
answered_at   # ⭐ 用户实际答题的时刻（客户端时间）
created_at    # 记录入库的时刻（服务器时间）
```

回放必须按 `answered_at` 排序，**不能**按 `created_at` 或自增 ID。
因为离线答的题可能几小时后才上传 —— 入库顺序 ≠ 真实发生顺序。

---

## 白送的好处

一旦你有了完整的事件历史，很多功能**不用额外开发**：

| 功能 | 怎么实现 |
|------|---------|
| 错题本 | 筛选 `is_correct = false` 的事件 |
| "你总把 accommodate 拼成 accomodate" | 聚合同一个词的 `user_input` |
| 学习曲线图 | 按天聚合事件数量和正确率 |
| 连续学习天数 | 按天 distinct 计数 |
| 换了算法要重建进度 | 用新算法重放一遍全部事件 |

最后一条特别值钱：**你可以改算法而不丢数据。**
今天用 Leitner，明年想换 SM-2？重放一遍就行，历史进度完整重建。
如果只存状态，这是做不到的 —— 你根本不知道用户当初答对还是答错。

---

## 纯事件溯源的问题：慢

每次查"今天该复习哪些词"，都要把全部历史事件拉出来回放一遍？
4000 个词 × 每个词几十条事件 = 每次查询几万条记录。**太慢了。**

---

## 本项目的方案：混合式

**两张表，各司其职：**

```
┌────────────────────────────┐         ┌──────────────────────┐
│      answer_events         │         │    user_progress     │
│                            │  回放   │                      │
│   事实来源                  │ ──────> │   缓存               │
│   只追加，永不改             │         │   可以随时删了重建     │
│   完整历史                  │         │   查询快              │
└────────────────────────────┘         └──────────────────────┘
        ↑                                        ↑
   每次答题写这里                          平时查询读这里
```

| 场景 | 走哪条路 |
|------|---------|
| 用户答题 | 追加事件 + 增量更新缓存 |
| 查今日任务 | 直接读缓存（一次索引查询，快） |
| 多端冲突 | 从事件回放重算，覆盖缓存 |
| 算法改了 | 全量回放重建 |
| 怀疑数据脏了 | 调 `/api/progress/rebuild` |

**这样既有事件溯源的正确性，又有状态存储的速度。**

---

## 必须守住的铁律 ⚠️

> **`user_progress` 表的每一行，都必须能由 `answer_events` 完整重算出来。**

一旦某个功能往 `progress` 表里写了"事件里没有的信息"，比如：

```python
# ❌ 危险！这个 note 无法从事件重算
progress.user_note = "这个词老是记不住"
```

那么"删掉 progress 表能重建"这个性质就破了，整个设计的价值也就没了。

**遇到这种需求怎么办**：要么新增一种事件类型把它记进事件表，要么单独开一张表放，**不要污染 progress**。

---

## 代价（诚实地说）

事件溯源不是免费的：

- **复杂度**：写路径要维护两张表，比单表多一层心智负担
- **存储增长**：事件表只增不减（估算一个活跃用户一年几万条，本项目规模下不是问题）
- **时钟依赖**：`answered_at` 是客户端时间，用户手机时钟不准会污染回放顺序
  - 缓解（v2）：入库时若 `answered_at` 与 `created_at` 偏差超 24 小时，记录告警
- **容易被无意破坏**：新人（包括未来的你）很容易顺手往 progress 里塞点东西
