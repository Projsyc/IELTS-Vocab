> ADR = Architecture Decision Record，记录"为什么这么选"。
> **用途**：几个月后你（或别人）想推翻某个设计时，先看这里 —— 当时可能已经考虑过你现在想到的方案。

## ADR-001 用 pnpm workspace 而非 Turborepo / Nx

**2026-07-25** · ✅ 已采纳

### 背景

项目要在一个仓库里放 Web 前端、后端、以及未来的 Android 和微信小程序，需要 Monorepo 管理方案。

### 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| pnpm workspace | 零配置、pnpm 自带 | 无构建缓存，全量构建 |
| Turborepo | 增量构建、任务编排 | 多一层配置要学 |
| Nx | 功能最全、依赖图、代码生成器 | 重、学习曲线陡 |

### 决定

**pnpm workspace**。

### 理由

1. 开发者是编程新手，工具复杂度应该让位于学习成本
2. 项目早期改动频繁、代码量小，构建缓存收益微乎其微
3. **pnpm workspace 可以无缝升级到 Turborepo** —— 加个 `turbo.json` 即可，不是单向门
4. 后端是 Python，本来就不在 JS 构建体系内，Turborepo 只能管一半

### 代价

- 项目变大后 `pnpm build` 会全量构建，变慢
- **触发升级的信号**：单次构建超过 30 秒，或 CI 时间成为瓶颈

## ADR-002 混合式事件溯源存储学习进度 ⭐

**2026-07-25** · ✅ 已采纳

> **这是本项目最重要的架构决定。** 它影响所有涉及"进度"的代码。

### 背景

需求要求多端（Web / Android / 小程序）同步学习进度。核心冲突场景：

> 用户在手机上离线背了 20 个词，同时在电脑上也背了。同一个单词两边的 Leitner 盒子号不一样。听谁的？

### 选项

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **A. 只存状态** | 只有 `progress` 表，存当前盒子号 | 最简单，读写都快 | 冲突无法正确解决，只能"后写的赢"，会丢数据 |
| **B. 取保守值** | 冲突时取盒子号小的 | 简单，不会误判掌握 | 治标不治本，用户的正确答题被丢弃 |
| **C. 纯事件溯源** | 只存事件，进度每次实时重算 | 最准确，历史完整 | 每次查询都要回放，词量大了慢 |
| **D. 混合式** | 事件表（事实）+ 进度表（缓存） | 兼顾准确与性能 | 两处数据要维护一致性 |

### 决定

**D. 混合式事件溯源。**

```
answer_events（只追加，事实来源）  ──回放──>  user_progress（缓存，可重建）
```

- 平时读 `progress` 表（一次索引查询，快）
- 多端冲突时从 `answer_events` 按 `answered_at` 回放重算
- 提供 `POST /api/progress/rebuild` 手动触发重算

### 理由

1. **正确性**：事件带客户端时间戳，回放能还原真实答题顺序，冲突有确定答案
2. **性能**：日常查询走缓存，不为极少发生的冲突付出常态代价
3. **意外收获**：完整答题历史免费送来了错题本、学习曲线、"你总是把 accommodate 拼成 accomodate"这类洞察 —— 这些用方案 A 都做不了
4. **可修复性**：算法参数改了（比如调整 Leitner 间隔），重放一遍就能重建全部历史进度。方案 A 做不到

### 代价

- **复杂度**：写路径要维护两张表，比单表多一层
- **不变式约束**：`progress` 表的每一行都必须能从事件重算出来。
  一旦有功能往 `progress` 写入事件里没有的信息，这个设计就破了 —— 这是最容易被无意破坏的地方
- **存储**：事件表持续增长（估算：一个活跃用户一年约几万条，暂不构成问题）
- **时钟依赖**：`answered_at` 用客户端时间，客户端时钟不准会污染回放顺序。
  缓解措施（v2）：入库时检测 `answered_at` 与 `created_at` 偏差超过 24h 则告警

### 实施要点

- Leitner 转移必须是**纯函数** `apply_answer(box, is_correct, at) -> (new_box, next_review)`
- 回放函数必须按 `answered_at` 排序，不能按 `created_at` 或自增 ID
- 单元测试要覆盖：乱序事件回放结果与顺序回放一致

## ADR-003 进度按 (用户, 单词, 模式) 三元组存储

**2026-07-25** · ✅ 已采纳

### 背景

应用有两种练习模式：听写（拼写）和阅读（认词义）。同一个单词在两种模式下的进度，是合并还是分开？

### 选项

- **A. 共享**：主键 `(user_id, word_id)`，一个词一个盒子号
- **B. 独立**：主键 `(user_id, word_id, mode)`，每种模式各一个盒子号

### 决定

**B. 独立。**

### 理由

"认得出"和"会拼写"是两种不同的能力：

> 你能一眼认出 `accommodate` 是"容纳"（阅读模式满分），
> 但让你拼出来可能少一个 `m`（听写模式不及格）。

如果合并，阅读模式的连续答对会把这个词推进高盒子，导致**本该反复练的拼写被误判为已掌握**，直接违背应用目的。

### 代价

- 进度表行数翻倍（4000 词 × 2 模式 × N 用户）—— 对目标用户规模完全不是问题
- 所有涉及进度的查询都要带 `mode` 参数，API 上稍显啰嗦
- 统计展示要分模式呈现，UI 复杂度略增

## ADR-004 Leitner 盒子而非 SM-2

**2026-07-25** · ✅ 已采纳

### 背景

需要间隔重复算法安排错词复习。

### 选项

| 方案 | 状态字段 | 复杂度 |
|------|---------|--------|
| Leitner 5 盒 | `box`（1 个整数） | 低 |
| SM-2（Anki 同款） | `ease_factor` / `interval` / `repetitions` | 中 |
| 当天轮次内重现 | 无需持久化 | 极低，但不是真正的间隔重复 |

### 决定

**Leitner 5 盒**，间隔 1 / 2 / 4 / 7 / 15 天。

- 答对 → 升一箱（Box 5 封顶）
- 答错 → **直接掉回 Box 1**（不是降一箱）

### 理由

1. 状态只需一个整数，事件回放逻辑极简，容易写对也容易测
2. 对新手足够有效 —— Leitner 是经过几十年验证的方法
3. 参数放配置文件，随时可调
4. **升级路径通畅**：因为有完整事件历史（ADR-002），将来换 SM-2 只需重放全部事件即可重建进度，不丢数据

### 代价

- 不如 SM-2 精细（SM-2 会根据"答得多轻松"动态调整间隔）
- "答错掉回 Box 1"比较严厉，Box 5 的词错一次就要从头来。
  实际使用后若觉得挫败感太强，可改为"降两箱"—— 改配置 + 重放即可

## ADR-005 前端用 Tailwind + shadcn/ui

**2026-07-25** · ✅ 已采纳

### 背景

开发者是前端新手，需要能快速做出可用界面，又不想被组件库锁死。

### 选项

- **Tailwind 纯手写**：自由但慢，新手做弹窗/输入框会痛苦
- **Tailwind + shadcn/ui**：组件代码复制进项目，可直接改
- **Ant Design**：开箱即用，但样式偏后台管理系统风格

### 决定

**Tailwind + shadcn/ui。**

### 理由

1. shadcn/ui **不是 npm 依赖，是把组件源码复制到你项目里** —— 想改直接改，不用跟库斗争
2. 新手能站在现成组件上起步，不用从零写按钮和输入框
3. 底层就是 Tailwind，学到的样式知识不浪费
4. Ant Design 的视觉风格更适合后台系统，背单词应用需要更轻快的观感

### 代价

- 组件代码在自己仓库里，**不会随上游自动更新**（想要新版本要手动同步）
- 初次配置比 Ant Design 多几步（Tailwind + 路径别名 + CLI 初始化）

## ADR-006 MVP 不做部署，不做用户上传词库

**2026-07-25** · ✅ 已采纳

### 背景

需求包含"给朋友用"（需公网部署）和"用户自定义上传词库"，但都不在 MVP。

### 决定

MVP 只在本地跑通完整链路，这两项延后到 v2。

### 理由

1. **个人项目最常见的死法是范围膨胀。** 先证明核心玩法能跑通，再谈分发
2. 用户上传词库表面简单，实际包含：文件上传、CSV 解析、格式校验、友好错误提示、词库权限模型、上传词无音频的降级 —— 是个独立的中型功能
3. 部署会引入运维、域名、备案、HTTPS、成本等一堆与核心玩法无关的问题

### 代价

- "给朋友用"这个目标在 MVP 阶段实现不了，只能自己用
- 数据库设计**已经为这两项预留**（`word_lists.owner_id` / `is_public`），v2 不用改表

## ADR-007 词库改用 ECDICT 的 ielts 子集，放弃刘洪波词表

**2026-07-25** · ✅ 已采纳 · 🔄 取代 [ADR 前的 PRD §4.1 假设](./01-product-spec.md)

### 背景

原计划以《刘洪波雅思词汇真经》的选词范围为参考，释义另找开源词典。但该书受版权保护，且 GitHub 上没有现成的词表仓库 —— 要用就得从受版权保护的 PDF 提取。

调研中发现 [ECDICT](https://github.com/skywind3000/ECDICT)（MIT，77 万词条）的 `tag` 字段自带考试大纲标注，其中 `ielts` 标签覆盖 **5,040 词**。

### 决定

**词表与释义全部来自 ECDICT 的 ielts 子集，5,040 词全部导入，不使用刘洪波词表。**

同时存下 `exam_tags`（`zk gk cet4 cet6 ky toefl gre`）和词频 `bnc`/`frq`。

### 理由

1. **版权问题直接消失** —— MIT 许可，可自由使用和再分发
2. 省掉"提取词表 → 匹配释义"的整个环节，M1 立刻能开工
3. 全量导入而非筛选：导入不做取舍，"练哪些"变成应用层筛选器（可选"跳过四级词"），更灵活且零成本。Leitner 会自动把简单词推进 Box 5 不再出现
4. 不按词频取前 N：BNC 前列是 `in` `on` `say` `as` `get`，雅思考生不需要背，纯频率排序会挤掉真正该学的难词

### 代价

- 选词范围不是刘洪波那本书的 —— 5,040 词里有 641 个中考词、1,713 个高考词，对备考雅思的人偏简单
- ECDICT 释义偏简略，部分带 `[计]`/`[经]` 领域标记
- 用户保留了"以后自己提供词形列表"的选项（[决策记录](./09-wordlist-research.md)），届时用它去 ECDICT 匹配即可，表结构不用改

## ADR-008 一词多义：`meaning` + `meaning_primary` 双字段

**2026-07-25** · ✅ 已采纳

### 背景

实测 ECDICT ielts 子集中 **75.1% 是多义词**（平均 2.06 个义项，最多 6 个）。原数据模型只有单个 `meaning TEXT` 字段。

### 选项

| 方案 | 问题 |
|------|------|
| 只存完整释义，运行时切首义 | 每次出题都要切字符串 |
| 只存第一义项，丢弃其余 | `abstract` 只剩"抽象的"，丢了名词/动词义，学习价值受损 |
| 拆 `word_senses` 独立表 | 最规范，但干扰项生成、进度统计全要重新设计，MVP 不值 |
| **双字段** | 多一列 |

### 决定

**`meaning` 存完整释义，`meaning_primary` 存第一义项，导入时算好。**

- 阅读模式的 4 个选项用 `meaning_primary`
- 答题后展示 `meaning` 完整释义

### 理由

实测长度数据决定了这个选择：

| | 中位数 | 最长 | 超 40 字占比 |
|---|---|---|---|
| 完整释义 | 27 字 | 169 字 | — |
| 第一义项 | **14 字** | 83 字 | **1.6%** |

1. 完整释义太长，4 个选项堆在屏幕上难读
2. **更关键**：完整释义长度差异极大（11–169 字）。如果正确答案系统性地比干扰项长或短，**长度本身就泄露了答案**。首义长度均匀，消除这个信号
3. 不丢数据 —— 答题后仍能看到全部义项
4. 导入时算好，查询不用现切

### 代价

- 多一列，存储翻倍（对 5,040 行完全不是问题）
- 首义与完整释义存在冗余，若日后要修订释义需同时改两处（seed 脚本重跑即可）

## ADR-012 话题体系：20 个雅思话题 + 1 个兜底，LLM 打标

**2026-07-25** · ✅ 已采纳 · 已完成打标并人工验收

### 背景

阅读模式要从**同话题**内抽 3 个干扰项（[ADR-003](#)）。调研确认没有任何现成数据源提供雅思话题分类（GitHub 搜 "ielts vocabulary topic" → 0 结果），只能用 LLM 打标。

需要先定两件事：用哪些话题类别、话题中立的词怎么办。

### 决定

**20 个雅思写作/口语常见话题 + `通用/抽象` 兜底，共 21 类。**

```
教育  环境  科技  健康与医疗  工作与职业  商业与经济
政府与社会  法律与犯罪  文化与传统  媒体与广告  交通
城市与住房  家庭与人际  旅游  体育与休闲  艺术
食物与农业  动物与自然  语言  全球化
通用/抽象  ← 兜底
```

每个话题在 `TOPIC_HINTS` 里附**边界说明**（如"环境 —— 污染、气候变化、能源、资源、生态、可持续"）。

LLM 用 DeepSeek `deepseek-v4-flash`，OpenAI 兼容接口，配置全在 `.env`。

### 理由

1. **兜底类是必须的** —— 强行把 `abundant` `accurate` `criterion` 塞进具体话题只会产出垃圾标签，反而降低干扰项质量。实测兜底占 39.3%（1,872 词），抽查确认这些词确实话题中立
2. **21 类的粒度合适** —— 4,768 ÷ 21 ≈ 227 词/类，抽 3 个干扰项余量充足（实测最少的 `全球化` 也有 27 词）
3. **带边界说明显著降低误标** —— 不加说明时多义词（`bank` 银行/河岸）容易判错
4. **白名单严格校验** —— LLM 返回白名单外的标签一律拒收、不写入。
   `normalize_topic()` 只做保守清理（去空格/引号/`类``话题`等后缀），
   **认不出就返回 None**，不做模糊匹配 —— 猜错比留空更糟，留空还能被重跑捡起来
5. **单话题而非多话题** —— 匹配现有 `topic VARCHAR(50)` 字段，不引入关联表

### 实测结果

```
覆盖率     4,768 / 4,768  (100%)
拒绝标签   0     ← prompt 有效，LLM 全部照白名单输出
漏词       0
批失败     0
耗时       0.7 分钟（157 请求，并发 128）
token      prompt 183,760 + completion 237,590
```

### 人工验收（路线图上最后一个未验证风险）

| 检查项 | 结果 |
|--------|------|
| 随机 45 条 | ~38 明确正确、5 边界模糊、**1 错**（`panel→教育`，按第三义项判断） |
| 反查 14 个明确该有话题的词 | **14/14 全对**（`surgery→健康`、`tuition→教育`、`referee→体育`…） |
| 兜底类 30 条抽查 | 确实都是话题中立词，2–3 个边界（`compute` 可算科技） |
| 干扰项功能测试 | ✅ 同话题词语义相关（`intersection` → 自行车/运输/飞行） |

**明确错误率 2–5%**，低于预设的 10% 阈值 → 验收通过。

### 已知局限

- **LLM 偶尔按非主要义项判断**：`panel` 的主义项是"嵌板/仪表板"，
  但因第三义项"专题讨论小组"被标进「教育」
- 边界情况约 10–15%，但那些是人类也会分歧的判断（`devise` 算科技还是通用？）
- 影响可控：即使误标，那个词仍能当一个"合理但错误"的干扰项，不会毁掉题目

### 代价与后续

- 换话题体系或改 prompt 后**必须重新抽样校验**，`--retag <话题>` 支持局部重打
- **发现了一个下游问题**：干扰项查询必须同时按 `part_of_speech` 过滤，
  否则释义前缀（`n.` / `vt.`）会泄露答案。详见
  [03-data-model.md §5](./03-data-model.md)，M2 实现时处理

## ADR-011 提交 1.5MB 雅思子集，不提交 66MB 完整 ECDICT

**2026-07-25** · ✅ 已采纳 · 🔄 修正了本次会话中"全部忽略源数据"的初始做法

### 背景

seed 脚本最初的设计是：源数据不进 git，运行时从 `raw.githubusercontent.com` 的 `master` 分支自动下载（66MB）。

用户对此提出质疑，核心是三个问题：

1. **别人（或换台机器的我）能从头构建这个项目吗？**
2. 数据库能持久化吗？—— 如果不能，源数据不在仓库里就意味着构建链断了
3. 逻辑上，如果不提交原始数据，那处理原始数据的脚本似乎也不该提交

### 审视原方案

第 1 点原方案其实是满足的 —— `ensure_ecdict()` 会自动下载，fresh clone 能跑通。
第 3 点两者并不对称（脚本是行为的源头，数据是输入），但**背后的原则成立：构建依赖的东西应该在自己掌控之下**。

而质疑命中了一个原方案确实存在的洞：

> **从 `master` 下载 = 没有锁版本。**
> 上游 ECDICT 一更新，文档里那些实测数字（5,040 词 → 剔 272 → 4,768）就静默失效，
> 而这些数字是写进 ADR-007 和 ADR-010 的依据。将来对不上会极难排查。

### 关键观察

完整版 66MB 里，**99.3% 是我们永远不会碰的非雅思词**。实测三种方案的体积：

| | 大小 | 行数 |
|---|---|---|
| 完整 `ecdict.csv` | 65.9 MB | 770,611 |
| **ielts 子集，保留全部列** | **1.5 MB** | 5,040 |
| ielts 子集，只留用到的 7 列 | 0.7 MB | 5,040 |

### 决定

**提交 `backend/data/ecdict-ielts.csv`（1.5MB，5,040 行，保留 ECDICT 全部列）。**

- 完整版 `ecdict.csv` 继续忽略 —— 它只是构建缓存
- 新增 `app/scripts/export_ielts_subset.py` 负责导出，并支持 `--verify` 校验一致性
- 下载兜底源**锁定 commit SHA**（`bc015ed2…`）而非 `master`
- seed 脚本按优先级取数据：仓库子集 → 完整版 → 才下载
- `backend/data/README.md` 记录溯源信息（上游 commit、导出日期、sha256）与数据陷阱

### 理由

1. **fresh clone 离线可复现** —— 不依赖第三方仓库还活着
2. **等于锁定数据版本** —— 数据就在仓库里，实测数字永远对得上；
   若上游更新，`test_inflection_filter_on_real_wordlist` 会因断言不符而失败，
   这是**刻意的保护**而非脆弱的测试
3. **1.5MB git 完全扛得住** —— GitHub 单文件 50MB 才警告、100MB 才拒绝
4. **许可允许** —— ECDICT 是 MIT，可自由再分发
5. **保留全部列**而非精简到 7 列 —— 多出的 0.8MB 无所谓，
   以后想用 `definition`（英文释义）/ `collins`（星级）时不必重新导出

### 代价

- 仓库多 1.5MB，且会永久留在 git 历史里
- 上游 ECDICT 更新时需手动重新导出并复核文档数字（流程写在 `backend/data/README.md`）
- 子集与完整版存在冗余：若两个文件都在本地，得记住 seed 优先读子集

### 顺带明确的一件事

**数据库是产物，不是真相来源。** Docker 数据卷会持久化，但 `pnpm db:reset` 会删、换机器不会跟着走。完整重建路径（已写进 `backend/data/README.md`）：

```bash
pnpm install && cp backend/.env.example backend/.env
pnpm db:up && pnpm db:migrate && pnpm seed
```

音频（~100MB）同理，是 seed 阶段 2/3 的产物，不进 git。

## ADR-010 剔除冗余屈折形式，词库定为 4,768 词

**2026-07-25** · ✅ 已采纳

### 背景

写 seed 脚本时试跑 40 词，发现 4 个词没有音标。查下去发现是 `accidents`、`accommodations`、`accountants`、`account for` —— **复数形式和短语**。

进一步统计（实测 5,040 词全量）：

| 类别 | 数量 |
|------|------|
| 屈折形式且原型也在词表里 | **272** |
| 屈折形式但原型不在词表里 | 156 |
| 专有名词 | 66 |
| 短语 | 2 |

`accommodations` 和 `accommodation` 同时存在，让用户分别背两次没有额外价值；而且屈折形式在 dictionaryapi.dev 里查不到，音标和真人音频都会缺失。

### 决定

**只剔除那 272 个"原型也在词表里"的屈折形式，其余全部保留。最终 4,768 词。**

识别方式：ECDICT 的 `exchange` 字段中 `0:xxx` 表示"本词是 xxx 的变形"。

### 理由

1. **272 个是纯冗余** —— 原型已在词表里，剔了不丢任何词汇量
2. **156 个必须保留** —— 它们的原型不在词表中（只以屈折形式被收录），剔了就是丢词
3. **66 个专有名词保留** —— `Africa` `April` `AIDS` 这类在雅思听力填空里是真考点，拼写也要练
4. **2 个短语保留** —— `account for` `bring about` 是有用的短语动词

### 代价

- 词库从 5,040 降到 4,768（-5.4%）
- 保留的 156 个屈折形式仍会缺音标/真人音频，靠 edge-tts 兜底
- 剔除逻辑需要**两趟扫描** csv（要判断原型是否在表内，得先知道全集）——
  多一次 63MB 文件遍历，几秒钟，可接受

### 验证

`tests/test_ecdict.py::test_inflection_filter_on_real_wordlist` 在真实数据上断言
5,040 → 剔 272 → 剩 4,768，并逐个检查**每个被剔的词其原型都还在保留集里**。

## ADR-009 音频与音标：dictionaryapi.dev 为主，edge-tts 兜底，全部本地化

**2026-07-25** · ✅ 已采纳

### 背景

ECDICT 的 `audio` 字段全空，`phonetic` 字段虽有 95.1% 覆盖但存在两个问题：混入西里尔字母（49.4% 词条），且整套记音体系不是现代 IPA。

### 实测数据

| 方案 | 覆盖率 | 延迟 | 许可 |
|------|--------|------|------|
| dictionaryapi.dev 音频 | 70–76% | 中位 **760ms** | 免费社区服务，无明确再分发许可 |
| dictionaryapi.dev IPA | **96%** | 同上（同一请求） | 同上 |
| edge-tts | 100% | 本地生成 | 库 LGPL-3.0；微软端点无公开开发者协议 |
| 浏览器 SpeechSynthesis | 100% | 实时 | ✅ 零风险，但音质一般、各端不一致 |

音频 100% 托管在 `api.dictionaryapi.dev` 单一主机。

### 决定

**seed 阶段全部本地化：**

```
音频  76% dictionaryapi.dev 真人发音  +  24% edge-tts  →  100% 本地
音标  96% dictionaryapi.dev 真 IPA    +   4% 清洗版 ECDICT  →  100%
```

音标额外做 `ɹ`(U+0279) → `r` 归一化。

### 理由

1. **760ms 延迟让热链不可用** —— 听写时点"播放"要等近 1 秒，核心交互被毁
2. 单一免费社区服务热链既是单点故障，也是对人家的骚扰。下载缓存反而更礼貌
3. 音标改从 API 取是**零额外成本** —— 本来就要为每个词调它拿音频
4. **原计划"把 ECDICT 音标规范化成标准 IPA"经实测不可行**：规则转换后 0/8 与标准 IPA 一致。ECDICT 用简化记音（`i` vs `ɪ`、`ei` vs `eɪ`、`әu` vs `əʊ`），而单个 `i` 无法从字符判断该转成什么，取决于具体单词

### 代价

- **许可风险未消除**：两个音频来源的再分发权都不明确。本地自用可接受，**v2 公网部署前必须复核**
  - 退路：改用浏览器 `SpeechSynthesis`，改动量是一个字段判空 + 前端降级分支
- 存储 ~100 MB 音频（不进 git）
- seed 第 4 步耗时约 **75 分钟**（5,040 词 × ~0.9s，需限速）→ **脚本必须支持断点续跑**
- 依赖两个外部服务的可用性（仅 seed 阶段；导入后数据本地化，服务下线不影响运行）
