# 08 架构决策记录（ADR）

> ADR = Architecture Decision Record，记录"为什么这么选"。
> **用途**：几个月后你（或别人）想推翻某个设计时，先看这里 —— 当时可能已经考虑过你现在想到的方案。

---

```markdown
## ADR-XXX 标题

**日期** · **状态**：✅ 已采纳 / 🔄 已被 ADR-YYY 取代 / 💭 提议中

### 背景
（面临什么问题）

### 选项
（考虑过哪些方案，各自代价）

### 决定
（选了哪个）

### 理由
（为什么）

### 代价
（这个选择的坏处，诚实写）
```

## ADR-001 用 pnpm workspace 而非 Turborepo / Nx

**2026-07-25** · ✅ 已采纳

### 背景

项目要在一个仓库里放 Web 前端、后端、以及未来的 Android 和微信小程序，需要 Monorepo 管理方案。

### 选项

| 方案 | 优点 | 缺点 |
|------|------|------|
| pnpm workspace | 零配置、pnpm 自带 | 无构建缓存，全量构建 |
| Turborepo | 增量构建、任务编排 | 多一层配置要学 |
| Nx | 功能最全、依赖图、代码生成器 | 重、学习曲线陡 |

### 决定

**pnpm workspace**。

### 理由

1. 开发者是编程新手，工具复杂度应该让位于学习成本
2. 项目早期改动频繁、代码量小，构建缓存收益微乎其微
3. **pnpm workspace 可以无缝升级到 Turborepo** —— 加个 `turbo.json` 即可，不是单向门
4. 后端是 Python，本来就不在 JS 构建体系内，Turborepo 只能管一半

### 代价

- 项目变大后 `pnpm build` 会全量构建，变慢
- **触发升级的信号**：单次构建超过 30 秒，或 CI 时间成为瓶颈

## ADR-002 混合式事件溯源存储学习进度 ⭐

**2026-07-25** · ✅ 已采纳

> **这是本项目最重要的架构决定。** 它影响所有涉及"进度"的代码。

### 背景

需求要求多端（Web / Android / 小程序）同步学习进度。核心冲突场景：

> 用户在手机上离线背了 20 个词，同时在电脑上也背了。同一个单词两边的 Leitner 盒子号不一样。听谁的？

### 选项

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **A. 只存状态** | 只有 `progress` 表，存当前盒子号 | 最简单，读写都快 | 冲突无法正确解决，只能"后写的赢"，会丢数据 |
| **B. 取保守值** | 冲突时取盒子号小的 | 简单，不会误判掌握 | 治标不治本，用户的正确答题被丢弃 |
| **C. 纯事件溯源** | 只存事件，进度每次实时重算 | 最准确，历史完整 | 每次查询都要回放，词量大了慢 |
| **D. 混合式** | 事件表（事实）+ 进度表（缓存） | 兼顾准确与性能 | 两处数据要维护一致性 |

### 决定

**D. 混合式事件溯源。**

```
answer_events（只追加，事实来源）  ──回放──>  user_progress（缓存，可重建）
```

- 平时读 `progress` 表（一次索引查询，快）
- 多端冲突时从 `answer_events` 按 `answered_at` 回放重算
- 提供 `POST /api/progress/rebuild` 手动触发重算

### 理由

1. **正确性**：事件带客户端时间戳，回放能还原真实答题顺序，冲突有确定答案
2. **性能**：日常查询走缓存，不为极少发生的冲突付出常态代价
3. **意外收获**：完整答题历史免费送来了错题本、学习曲线、"你总是把 accommodate 拼成 accomodate"这类洞察 —— 这些用方案 A 都做不了
4. **可修复性**：算法参数改了（比如调整 Leitner 间隔），重放一遍就能重建全部历史进度。方案 A 做不到

### 代价

- **复杂度**：写路径要维护两张表，比单表多一层
- **不变式约束**：`progress` 表的每一行都必须能从事件重算出来。
  一旦有功能往 `progress` 写入事件里没有的信息，这个设计就破了 —— 这是最容易被无意破坏的地方
- **存储**：事件表持续增长（估算：一个活跃用户一年约几万条，暂不构成问题）
- **时钟依赖**：`answered_at` 用客户端时间，客户端时钟不准会污染回放顺序。
  缓解措施（v2）：入库时检测 `answered_at` 与 `created_at` 偏差超过 24h 则告警

### 实施要点

- Leitner 转移必须是**纯函数** `apply_answer(box, is_correct, at) -> (new_box, next_review)`
- 回放函数必须按 `answered_at` 排序，不能按 `created_at` 或自增 ID
- 单元测试要覆盖：乱序事件回放结果与顺序回放一致

## ADR-003 进度按 (用户, 单词, 模式) 三元组存储

**2026-07-25** · ✅ 已采纳

### 背景

应用有两种练习模式：听写（拼写）和阅读（认词义）。同一个单词在两种模式下的进度，是合并还是分开？

### 选项

- **A. 共享**：主键 `(user_id, word_id)`，一个词一个盒子号
- **B. 独立**：主键 `(user_id, word_id, mode)`，每种模式各一个盒子号

### 决定

**B. 独立。**

### 理由

"认得出"和"会拼写"是两种不同的能力：

> 你能一眼认出 `accommodate` 是"容纳"（阅读模式满分），
> 但让你拼出来可能少一个 `m`（听写模式不及格）。

如果合并，阅读模式的连续答对会把这个词推进高盒子，导致**本该反复练的拼写被误判为已掌握**，直接违背应用目的。

### 代价

- 进度表行数翻倍（4000 词 × 2 模式 × N 用户）—— 对目标用户规模完全不是问题
- 所有涉及进度的查询都要带 `mode` 参数，API 上稍显啰嗦
- 统计展示要分模式呈现，UI 复杂度略增

## ADR-004 Leitner 盒子而非 SM-2

**2026-07-25** · ✅ 已采纳

### 背景

需要间隔重复算法安排错词复习。

### 选项

| 方案 | 状态字段 | 复杂度 |
|------|---------|--------|
| Leitner 5 盒 | `box`（1 个整数） | 低 |
| SM-2（Anki 同款） | `ease_factor` / `interval` / `repetitions` | 中 |
| 当天轮次内重现 | 无需持久化 | 极低，但不是真正的间隔重复 |

### 决定

**Leitner 5 盒**，间隔 1 / 2 / 4 / 7 / 15 天。

- 答对 → 升一箱（Box 5 封顶）
- 答错 → **直接掉回 Box 1**（不是降一箱）

### 理由

1. 状态只需一个整数，事件回放逻辑极简，容易写对也容易测
2. 对新手足够有效 —— Leitner 是经过几十年验证的方法
3. 参数放配置文件，随时可调
4. **升级路径通畅**：因为有完整事件历史（ADR-002），将来换 SM-2 只需重放全部事件即可重建进度，不丢数据

### 代价

- 不如 SM-2 精细（SM-2 会根据"答得多轻松"动态调整间隔）
- "答错掉回 Box 1"比较严厉，Box 5 的词错一次就要从头来。
  实际使用后若觉得挫败感太强，可改为"降两箱"—— 改配置 + 重放即可

## ADR-005 前端用 Tailwind + shadcn/ui

**2026-07-25** · ✅ 已采纳

### 背景

开发者是前端新手，需要能快速做出可用界面，又不想被组件库锁死。

### 选项

- **Tailwind 纯手写**：自由但慢，新手做弹窗/输入框会痛苦
- **Tailwind + shadcn/ui**：组件代码复制进项目，可直接改
- **Ant Design**：开箱即用，但样式偏后台管理系统风格

### 决定

**Tailwind + shadcn/ui。**

### 理由

1. shadcn/ui **不是 npm 依赖，是把组件源码复制到你项目里** —— 想改直接改，不用跟库斗争
2. 新手能站在现成组件上起步，不用从零写按钮和输入框
3. 底层就是 Tailwind，学到的样式知识不浪费
4. Ant Design 的视觉风格更适合后台系统，背单词应用需要更轻快的观感

### 代价

- 组件代码在自己仓库里，**不会随上游自动更新**（想要新版本要手动同步）
- 初次配置比 Ant Design 多几步（Tailwind + 路径别名 + CLI 初始化）

## ADR-006 MVP 不做部署，不做用户上传词库

**2026-07-25** · ✅ 已采纳

### 背景

需求包含"给朋友用"（需公网部署）和"用户自定义上传词库"，但都不在 MVP。

### 决定

MVP 只在本地跑通完整链路，这两项延后到 v2。

### 理由

1. **个人项目最常见的死法是范围膨胀。** 先证明核心玩法能跑通，再谈分发
2. 用户上传词库表面简单，实际包含：文件上传、CSV 解析、格式校验、友好错误提示、词库权限模型、上传词无音频的降级 —— 是个独立的中型功能
3. 部署会引入运维、域名、备案、HTTPS、成本等一堆与核心玩法无关的问题

### 代价

- "给朋友用"这个目标在 MVP 阶段实现不了，只能自己用
- 数据库设计**已经为这两项预留**（`word_lists.owner_id` / `is_public`），v2 不用改表
